# ClipVault 系统设计与技术选型

## 一、需求分析与建模

### 核心领域模型

从项目需求出发，抽象出三个实体：

| 实体 | 职责 | 关键决策 |
|---|---|---|
| **Share（分享）** | 一次分享的全部状态 | 文本与文件统一建模：`content_type` 区分，文件类只填 `file_*` 字段，避免两套几乎相同的表 |
| **User（用户）** | 可选账号体系 | `Share.user_id` 可空 —— **匿名是默认路径，登录只是增强**，与项目书"完全匿名"要求不冲突 |
| **AccessLog（访问日志）** | 访问统计 | 只存时间戳不存 IP，"隐私友好"作为设计约束而非事后补丁 |

### 生命周期状态机

```
           ┌────────── 手动销毁（delete_token / 登录身份）──────────┐
           │                                                        ▼
 [创建] ──► [有效] ──访问──► [计数+1] ── 达上限 ──► [物理删除：记录+磁盘文件]
           │                                                        ▲
           └────────────── 过期（后台任务5分钟扫描）───────────────┘
```

**关键设计：到期/达限不是"标记失效"，而是物理删除。**
理由：这是隐私产品的核心卖点（服务器不留痕迹），同时简化状态管理——
查询只有两种结果：拿到内容 / 不存在。

## 二、关键技术决策

### 1. 短码生成：为什么用 `secrets` 而不是自增 ID 或时间戳？

- 自增 ID 可预测（`/s/aaaaaaab` 遍历即可拖库全部内容）
- `secrets` 是密码学安全随机数发生器（操作系统熵源）
- 8 位 Base62 = 62⁸ ≈ 2.2×10¹⁴ 组合，暴力猜测需要 ~3.5 万年（100 req/s）
- 唯一性用数据库唯一索引保证，碰撞时重试（实测碰撞概率 < 10⁻¹⁰）

### 2. 并发安全的访问计数

**问题**：`max_views=5` 时，10 个并发请求同时读到 `view_count=4`，都判断"还能访问"，全部放行 → 超限。

**方案**：把"读-判断-写"合并成一条原子 UPDATE：

```sql
UPDATE shares SET view_count = view_count + 1
WHERE id = ? AND (max_views IS NULL OR view_count < max_views);
```

`rowcount == 0` 即说明已达上限。这条 SQL 由数据库的行锁保证原子性，
是"check-and-set"模式的标准应用。

**开发中实际踩的坑**：SQLAlchemy 2.0 的 `execute(update(...))` 默认
`synchronize_session="auto"` 会把 session 中对象的属性同步为更新后的值，
导致后续 `share.view_count + 1` 重复加一（首次访问计数就是 2）。修复方式：
`.execution_options(synchronize_session=False)` + 先读旧值手动 +1。

### 3. XSS 的纵深防御（三层）

| 层 | 机制 |
|---|---|
| 后端 | `Content-Security-Policy` 等安全响应头，即使注入成功也限制脚本执行 |
| 前端-纯文本 | 全部用 `el.textContent = data.content` 赋值，**存储原文 + 展示层转义**，浏览器自动转义 |
| 前端-Markdown | `marked.parse()` 允许原始 HTML → 必须再过 `DOMPurify.sanitize()` 白名单清洗 |

> 为什么后端不转义而存原文？① 端到端加密场景存的就是密文；② 转义是**展示关注点**，
> API 原样返回数据，由各端自行处理（与 Web 安全最佳实践一致）。

### 4. 端到端加密：密钥放哪？

**威胁模型**：不信任服务器管理员 / 数据库泄露。

**方案**：
```
加密（浏览器）：明文 --AES-256-GCM(随机key)--> 密文
分享链接 = https://host/s/CODE#k=<key>
                                  ^^^ URL fragment，浏览器规范：不随 HTTP 请求发送
服务器只存：密文。解密只发生在持有 #key 的浏览器里。
```

- AES-GCM 自带完整性校验（错误密钥 → 解密抛异常而非乱码）
- Web Crypto API（`crypto.subtle`）需要安全上下文：HTTPS 或 localhost

### 5. 文件存储：防路径遍历

用户文件名**只用于展示**，存储名由服务端生成 UUID —— 用户输入与文件系统路径完全隔离。展示名入库前再清洗一次（去路径成分 + 替换控制字符）。

### 6. SQLite 的取舍

- ✅ 单文件、零配置、随代码备份，日活 < 1k 的场景绰绰有余
- ⚠️ 写并发受限（单写锁）——但本项目写操作极轻（一条 UPDATE）
- 迁移路径：`DATABASE_URL` 环境变量切换 PostgreSQL，ORM 层零改动

## 三、API 设计

RESTful 风格要点：

- 资源化路径：`/api/shares/{code}`、`/api/files/{code}/download`
- 语义化状态码：`404` 不存在、`410` 已过期/已耗尽、`401` 未登录、`403` 无权、`413` 文件过大、`422` 参数错误
- `meta` 与 `content` 分离：查看文件卡片需要元信息但不应消耗访问次数
- FastAPI 自动生成 `/docs`（Swagger UI）——交付物中的 API 文档即为此

## 四、可观测与运维

- 后台清理任务（`lifespan` 启动的 `asyncio` 协程）：每 5 分钟物理删除过期分享 + 30 天以上访问日志
- 文件下载烧毁用 `BackgroundTask`：先完整发送响应、再删数据库与磁盘文件，规避 Windows 文件占用
- systemd `Restart=always` 保证进程自愈；Nginx 承担反代 + `client_max_body_size` 一层过滤
