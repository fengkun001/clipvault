# ClipVault 开发心得与问题解决记录

> 本文档记录开发过程中的关键问题、排查思路与收获，也作为复盘沉淀。

## 1. SQLAlchemy 同步策略导致的"幽灵 +1"

**现象**：分享设置 `max_views=3`，仅访问 2 次后第 3 次就被拒绝，且第一次访问返回的计数就是 2。

**排查**：用干净的 Python 脚本（排除 PowerShell 测试工具干扰）复现，确认是服务端逻辑问题。审查代码发现：

```python
result = db.execute(update(Share).values(view_count=Share.view_count + 1))
new_count = share.view_count + 1   # ← 这行出问题
```

SQLAlchemy 2.0 中 `execute(update(...))` 的 `synchronize_session` 默认为 `auto`，执行后会**把 session 中对象的属性同步为更新后的新值**。所以第二行的 `share.view_count` 已经是 +1 之后的值，再加一就多算了。

**修复**：
```python
old_count = share.view_count
db.execute(update(...).execution_options(synchronize_session=False))
new_count = old_count + 1
```

**收获**：ORM 是"方便"与"透明度"的权衡。理解 session 的同步语义，比背 API 更重要。这类 bug 的教训是：**写测试要断言精确值**，第一次手测时"能访问"掩盖了计数错误。

## 2. Windows 文件占用 vs 下载后烧毁

**现象设计**：文件分享达到下载上限时，希望"最后一次下载完成后"自动删除服务器文件。

**问题**：如果先删文件再返回响应，`FileResponse` 还没开始读文件就找不到文件了；Windows 上文件句柄未释放时 `unlink` 也会报错。

**方案**：Starlette 的 `BackgroundTask` —— 在**响应完全发送完毕后**才执行清理函数（删库记录 + 删磁盘文件），互不干扰。

```python
response = FileResponse(share.file_path, filename=share.file_name)
response.background = BackgroundTask(_finalize_download_burn, share.id, share.file_path)
```

**收获**：HTTP 框架的生命周期（请求 → 响应 → 后台任务 → 依赖清理）顺序是解决资源时序类问题的钥匙。

## 3. 端到端加密的密钥分发

**核心思考**：E2E 的难点从来不是"加密"（`crypto.subtle.encrypt` 一行搞定），而是**密钥如何送达接收方而不经过服务器**。

- 密钥放 URL `#fragment` —— 浏览器规范保证 fragment 不随请求发送 ✅
- 但意味着"谁拿到完整链接谁就能解密" —— 所以**链接本身就是授权**
- 服务器日志里只有 `/s/CODE`，看不到 `#key` 部分

**收获**：密码学工程中，密钥管理（生成、分发、销毁）比算法选择重要得多。这个设计还带来一个自然约束：E2E 模式下服务器无法做内容类型检测，所以解密后在前端再做启发式类型识别。

## 4. PowerShell 5.1 测试脚本的编码坑

**现象**：用 `Invoke-RestMethod` 发中文 JSON，服务端收到的全是 `æµè¯` 乱码。

**原因**：PowerShell 5.1 的 `-Body` 字符串默认按 ISO-8859-1 编码发送，即使 Content-Type 写了 `charset=utf-8`。

**解决**：测试脚本改用 Python `urllib`（显式 `.encode()` 成 bytes）——工具不可靠时，换一个行为透明的工具比跟它搏斗更高效。

## 5. 架构决策复盘：为什么"匿名优先"改变了整个设计

项目书同时要求"完全匿名分享"（基础版）与"用户系统"（拓展版），初看矛盾。解法是把匿名定为**默认路径**：

- `Share.user_id` 可空 —— 所有 API 对匿名用户 100% 可用
- 未登录：分享历史存 localStorage（销毁令牌也在本地）
- 已登录：同样创建分享，但额外获得云端管理 + 访问统计

这样两个需求不是二选一，而是同一模型上的两层能力。**好的数据建模让"矛盾需求"变成"分层能力"** —— 这是本项目最大的架构收获。
