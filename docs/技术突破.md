# ClipVault 开发心得与技术总结

## 一、项目背景与目标

ClipVault 是一个"干中学"的项目——目标不是造一个完美的产品，而是在实战中掌握 Web 全栈开发的完整链路：从需求分析、技术选型、编码实现，到安全加固、部署上线、线上排障。

**三个核心目标：**

1. **简历素材**：一个可以展示给面试官的完整项目，从代码到文档到线上运行
2. **商业化可能**：功能足够实用，技术上可扩展，不是"玩具项目"
3. **技术成长**：掌握 FastAPI + SQLAlchemy + Nginx + systemd 这条技术路线

## 二、技术突破

### 2.1 阅后即焚的并发安全

**问题本质：** 当一个分享的 `max_views=1` 时，两个用户同时打开链接，如何保证只有一个人看到？

**错误方案：** 先读 `view_count`，判断是否 < max_views，再写入 +1。这是典型的 **check-then-act** 竞态条件，两个并发请求可能都读到 `view_count=0`，都判断成立，都写入成功。

**正确方案：** 使用 SQLAlchemy 的条件更新（Conditional UPDATE），将"判断 + 写入"合并为一个原子操作：

```python
result = db.execute(
    update(Share)
    .where(
        Share.id == share.id,
        or_(Share.max_views.is_(None), Share.view_count < Share.max_views),
    )
    .values(view_count=Share.view_count + 1)
)
if result.rowcount == 0:
    # 另一个请求已经消耗了最后一次
    _burn(db, share)
```

**原理：** `WHERE view_count < max_views` 被翻译成 SQL 的 `WHERE view_count < max_views`，数据库在执行 UPDATE 时会对匹配的行加行锁。两个并发请求中，只有一个能满足 WHERE 条件，另一个的 `rowcount` 为 0。

**技术收获：** 理解"乐观锁"（Optimistic Locking）和"悲观锁"（Pessimistic Locking）的区别。本项目使用乐观锁——不提前加锁，而是在更新时检查条件，失败则处理冲突。这比 `SELECT ... FOR UPDATE` 的悲观锁更轻量，适用于冲突概率低的场景。

### 2.2 滑动窗口限流从零实现

**为什么不用第三方库：** 项目依赖已足够精简（7 个包），为限流引入 Redis 或 `slowapi` 会破坏"零依赖、易部署"的原则。

**实现思路：**

```python
class RateLimitMiddleware(BaseHTTPMiddleware):
    RULES = [
        ("POST", "/api/shares", 600, 30, "创建太频繁，请稍后再试"),
        ("POST", "/api/files", 600, 20, "上传太频繁，请稍后再试"),
    ]

    async def dispatch(self, request: Request, call_next):
        # 1. 根据 IP + 方法 + 路径前缀匹配规则
        # 2. 基于 deque 的滑动窗口计数
        # 3. 超过阈值返回 429
        # 4. 超 10000 个 key 时清理过期 IP 队列
```

**技术细节：**
- 使用 `time.monotonic()` 而非 `time.time()` 来避免系统时间跳变的影响
- 使用 `deque` 而非 `list` 来实现 O(1) 的左侧弹出
- 内存保护：超过 10000 个 IP 记录时清理 10 分钟无活动的条目

**技术收获：** 理解"滑动窗口"和"固定窗口"的区别。固定窗口（如"每分钟 60 次"）在窗口边界处有突发问题——第 59 秒和第 1 秒各发 60 次，在两秒内实际发出了 120 次。滑动窗口通过记录每个请求的时间戳，在过去 60 秒内精确计数，解决了这个问题。

### 2.3 文件名安全：从根上杜绝路径遍历

**问题：** 用户上传的文件名可能包含 `../`、绝对路径、特殊字符。

**错误方案：** 对文件名做黑名单过滤（如移除 `../`）——攻击者可以绕过（`....//`、`..\` 等变体）。

**正确方案：** 完全隔离——服务器生成 UUID 作为存储名，用户原始文件名仅用于展示：

```python
stored_name = uuid.uuid4().hex          # 服务器生成，与用户输入无关
store_path = settings.UPLOAD_DIR / stored_name

file_name = _sanitize_filename(file.filename)  # 仅展示用
```

**技术收获：** 安全设计的一个基本原则：**永远不要尝试"清洗"不安全的输入，而是将它替换为完全受控的值。** 清洗依赖"预测所有攻击方式"，替换则从根上消除了攻击面。

### 2.4 密码哈希的时序攻击防御

```python
def verify_password(password: str, stored: str) -> bool:
    dk = hashlib.pbkdf2_hmac("sha256", password.encode(), salt.encode(), int(iterations))
    return secrets.compare_digest(dk.hex(), hash_hex)
```

**为什么用 `secrets.compare_digest` 而不是 `==`：**

`==` 在字符串比较时，第一个不同字符处就会返回 False。攻击者可以通过测量响应时间的细微差异，逐字节推断出正确的哈希值——这就是时序攻击（Timing Attack）。

`secrets.compare_digest` 是恒定时间比较，无论两个字符串在第几位不同，耗时都相同，彻底消除了时序侧信道。

**技术收获：** 安全不只是"功能正确"，还包括"行为不可观测"。一个功能完全正确的密码验证，如果实现方式泄露了时间信息，就可能被攻破。

## 三、部署与排障纪实

详见 [部署排障报告](./deployment-bugfix-report.md)，这里概述几个关键教训。

### 3.1 Nginx 隐式目录重定向——一个 4 小时的精确定位

**故障：** 文件上传全部失败，但文本分享正常。

**排查路径：** 浏览器 → Nginx(80) → Uvicorn(8000) → 应用代码，逐层排除：

1. 直连 8000 端口 → 200 OK（应用层正常）
2. 经 Nginx 80 端口 → 301 Moved Permanently（Nginx 层有问题）
3. `nginx -T` 检查配置 → 无任何 return/rewrite 指令（排除显式重定向）
4. Nginx access.log 有 301 记录，应用日志无对应请求（请求被 Nginx 拦截）
5. 对比 `location /api/files/` 与实际请求 `POST /api/files`（不带斜杠）→ 定位到 Nginx 的隐式目录规范化行为

**教训：** 排查问题不要靠猜测，要靠"逐层排除"。每一步都拿出证据：日志、响应码、响应头。当证据指向"不可能"的方向时，说明你的知识边界需要扩展——Nginx 的隐式重定向就是一个"配置里看不到但确实存在"的行为。

### 3.2 僵尸进程——SO_REUSEPORT 的陷阱

`ss -tlnp` 显示 8000 端口上有三个进程，其中一个来自 9 月 4 日的手动启动。Uvicorn 的 `--workers 2` 使用 `SO_REUSEPORT`，内核把请求随机分发，导致请求有 1/3 概率落入旧代码。

**教训：** 永远不要让手动启动的进程和 systemd 管理的进程共存。部署脚本中加 `fuser -k` 是必须的防御措施。

### 3.3 reload vs restart

`systemctl reload nginx` 不会完全重新加载配置，某些情况下旧配置仍在内存中。`restart` 是唯一能保证配置生效的方式。

**教训：** 理解工具的语义差异。`reload` 是"尽量不中断服务地更新"，`restart` 是"完全重启"。在配置变更的正确性比服务中断的几秒钟更重要时，用 `restart`。

## 四、开发方法论

### 4.1 "先跑通，再完善"的迭代策略

项目开发遵循了这个节奏：

1. **MVP（最小可用）**：文本分享 + 短链 + 二维码 → 立即能用
2. **安全加固**：CSP、限流、SQL 参数化、XSS 防御 → 可以上线
3. **功能增强**：文件分享、自定义有效期、Markdown/代码高亮 → 体验提升
4. **部署上线**：Nginx 反代、systemd、一键部署脚本 → 生产就绪
5. **文档完善**：API 文档、架构说明、排障报告 → 交付物完整

每一步都有明确的产出，每一步都建立在"上一步确实跑通了"的基础上。

### 4.2 "治本不治标"的工程原则

三个部署 Bug 的修复都遵循了这个原则：

| 问题 | 治标做法 | 治本做法 |
|------|----------|----------|
| Nginx 301 | 手动改服务器配置 | 修改配置模板 + 部署脚本 |
| 僵尸进程 | 手动 kill | 部署脚本加 `fuser -k` |
| reload 不生效 | 记一条"注意事项" | 脚本改用 `restart` |

**"修一次"是运维，"修到不会再犯"才是工程。**

### 4.3 技术选型的最小化原则

整个项目的 Python 依赖只有 7 个包（FastAPI + Uvicorn + SQLAlchemy + python-multipart + aiofiles + Jinja2 + PyJWT），没有引入任何"大而全"的框架。

**原则：** 每引入一个依赖，就引入了一个版本冲突的可能、一个安全漏洞的风险、一个未来维护的负担。在功能满足的前提下，依赖越少越好。

## 五、个人心得

### 5.1 关于面试

ClipVault 这个项目，如果可能的话，我在面试中会这样介绍：

> "这是一个全栈 Web 项目，从零开始独立完成。技术栈包括 FastAPI、SQLAlchemy、Nginx、systemd。核心亮点包括：阅后即焚的并发安全设计（乐观锁）、滑动窗口限流的自实现、纵深防御的安全体系（CSP + 参数化查询 + 文件名隔离 + 时序攻击防御）。项目已在阿里云生产环境运行，经历过完整的部署排障流程。"

**面试官关心的不是"你做没做过"，而是"你遇到问题怎么解决的"。** 部署排障报告里的"分层诊断法"和"隐式重定向定位过程"，比"我会用 FastAPI"更有说服力。

### 5.2 关于独立开发

一个人做全栈项目，最大的挑战不是技术难度，而是**没有人帮你发现盲区**。代码审查、方案讨论、问题排查——这些在团队中有人分担的工作，独立开发时都要靠自己。

我的应对策略：
1. **写出来**：把排查过程、设计决策写下来，文字能暴露思维漏洞
2. **分步验证**：每完成一个模块就验证，不要等到最后一起测
3. **善用工具**：AI 辅助开发不是替代思考，而是加速"试错 → 验证 → 修正"的循环

### 5.3 关于"干中学"

这个项目让我真正理解了这些概念——不是"读过文档"，而是"写过代码、踩过坑、修过Bug"：

- **乐观锁**不是抽象的数据库理论，而是 `WHERE view_count < max_views` 这一行 SQL
- **CSP** 不是安全规范里的一个缩略词，而是 `response.headers["Content-Security-Policy"]` 这一行中间件代码
- **滑动窗口**不是算法题，而是 `deque` 从头弹出过期时间戳
- **时序攻击**不是论文里的概念，而是 `secrets.compare_digest` 替代 `==` 的工程决策

**真正的技术成长，发生在"我知道这个名词"变成"我写过这行代码"的时刻。**
